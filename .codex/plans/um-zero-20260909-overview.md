# Zero boundary debt and simpler UltraModern.js usage

**Plan only — implementation has not started.** This program extends the previous simplification work to all historical debt and to observable improvements in everyday usage and updates. Every implementation todo is pending; execution issues are deferred. Existing historical issue `modernjs-piop` remains the canonical zero-debt milestone. No subagents, framework changes, consumer migrations, upstream submissions, merge or publication are part of this planning turn.

## Acceptance contract

- The complete canonical divergence gate reports **zero violations**. Every initial and newly discovered historical identity has a lawful disposition. No budget reset, scope narrowing, audited identity rename or policy waiver makes this result green.
- The canonical import scan reports **zero current governed edges**, including currently allowlisted edges. Remove stale allowances after genuine repairs. This targets upstream-to-fork boundary dependencies, not normal imports throughout the framework.
- Fresh applications contain **zero copied framework runtime/checker implementations**. Keep necessary native entrypoints and contract data; consumers own their business source, topology and deployment choices.
- A same-contract update uses one documented existing entrypoint and changes dependencies, the lockfile and narrowly derived release identity data. It changes **zero consumer TS/JS or deployment-config files**, requires **zero manual source/config repair** on the supported success matrix, and is a no-op when repeated.
- Genuine older-schema/API changes have explicit one-time native migrations with a supported version floor, exact ownership checks, atomic failure/rollback and actionable conflicts. No permanent app compatibility wrapper or synthetic navigation fix.
- Real ERP-10, customized consumer and Tractor workflows pass on Node and workerd using the same source artifacts, then exact published bytes. Preserve Tractor's visible UI, native TanStack behavior, native Effect API identity and complete delivery-unit identity.
- Report actual generated artifacts, changed files, manual steps, duplicate checks, implementation/test/total LOC and measured time/RSS before and after. Moving code is not deleting code, and an ownership-only cleanup does not by itself establish simpler usage.

## Legal repair and unresolved decisions

The primary route is genuine fork ownership behind native upstream extension points. Audited identities remain governed even when moved. Neutral upstream fixes/extension points are prepared where legal fork edits cannot preserve behavior within the cap. Upstream submission requires explicit authorization when execution resumes, and upstream review/merge is a real external dependency.

The present provenance writer refuses upstreamRef advancement. A separate lane designs and proves an identity- and budget-preserving transition; normal growth/scope writers are not a workaround. Only actual accepted upstream source can change attribution. Every ambiguous row stays blocked until a legal route is proved. Thirteen audited identities had more than 20 lines of measured excess at the prior PR base; those counts warn about direct restoration but do not prove the minimum size of every alternative repair.

Freeze the actual supported migration/runtime floor before deleting v2/marker/published-wrapper paths. Preserve current emergency-age policy until evidence and the necessary product decision permit retirement; simplify duplicated ownership and recognition without weakening security. A still-required capability may remain in its proper owner, but no retained capability may retain a boundary violation. Optional retirement decisions must not hide mandatory debt or unnecessarily serialize independent repairs.

## Ownership and sequencing

The baseline inventory and usage contract are independent roots. After legal routes/interfaces are frozen, eight component ownership lanes, upstream proposal work, provenance support, generated-surface work and regression fixture preparation can progress independently. Package manifests/exports, lockfile, cohort and ledger each have one integration owner. Component workers provide exact shared-file patches instead of competing writes.

Generated-surface work releases update-transaction and native-usage work; legacy migrations follow the transaction contract. Packaging waits for actual required upstream landings, provenance support and component handoffs. The zero-gate milestone follows packaging and required retirement work. Final source integration then releases independent source and update acceptance. Publication follows both; published acceptance and closeout remain downstream.

No blanket two-agent limit or artificial global waves. Only launch workers after a later execution instruction and graph validation; each gets exact file ownership, stable interfaces, private mutable resources and a plan/br task. On one host the existing ERP and Tractor drivers share ports and must run serially; safe parallel execution requires genuinely isolated supported environments. Never remap apps with custom config solely to obtain apparent parallelism.
